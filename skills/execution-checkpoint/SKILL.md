# Execution checkpoint

**First load the official `planning-with-files` skill.** It owns plan selection, file creation, lifecycle hooks, and validation. This skill adds the PStack execution and reporting contract. Never duplicate its state engine or assume a remembered conversation is authoritative.

## Authorization and ownership

- Only execute when the user explicitly authorizes *implementation*. Approval of a spec, a plan, or a plan-gap interview alone does not authorize coding.
- Store execution state in the **repository being worked on**, not in the pstack plugin checkout. Keep the approved plan at `docs/plans/<name>.md` untouched; the separate `task_plan.md` is the execution ledger.
- Use a **named plan** in `.planning/<plan-id>/` for multi-step work. A single coordinator owns each run and the Markdown files. Delegated workers only report their evidence. For multiple simultaneous runs, pin `PLAN_ID` in the host environment or use separate worktrees; `.planning/.active_plan` is only a shared default.

## Starting or resuming

1. Read the approved plan and linked spec. Before initialization, find existing task state with the official `set-active-plan.sh --list` command. Reuse an existing run, never overwrite it.
2. If none exists, initialize using the official OpenCode `pwf_init` tool (when available), or the installed `planning-with-files/scripts/init-session.sh "<task name>"` from the **working repository**. Check the generated `PLAN_ID` and verify the selected root.
3. Copy the approved plan's tasks *as an execution checklist*, using `### Phase N: <task name>`, `- [ ] <step>`, and exactly one `**Status:** pending | in_progress | complete` line per phase. Keep `## Goal`, `## Current Phase` and `## Next Step`. Do not replace `task_plan.md` with an unparseable custom format. Validate with the official `check-complete.sh --validate <plan-path>`.
4. Preserve `progress.md` and `findings.md` generated by the initializer. Create `summary.md` beside them as a short **derived** status report.
5. **After a compaction or pickup:** resolve the selected plan, read all four files, then inspect the actual `git status`, `git diff`, recent commits and the recorded tests. Identify the last verified phase and next incomplete step. If the approved plan or evidence changed, report drift before continuing.

## Checkpoint every meaningful boundary

Immediately after a verified step, task/phase transition, failed check, blocker, important decision, or handoff:

- **`task_plan.md`**: update the exact checkbox, phase `**Status:**`, current phase, and one specific `## Next Step`. Only mark a phase complete when all of its steps have verifiable evidence.
- **`progress.md`**: append timestamp, task/step ID, changed artifacts and commit (if any), actual verification command and observed output, failure attempts, blockers, and next action. Log failures as failures, never as PASS.
- **`findings.md`**: keep research findings, architectural decisions with rationales, constraints and source/evidence pointers that must survive compaction.
- **`summary.md`**: update after each phase and before handoff: completion count, current state, outstanding work, latest verified evidence, open blockers (ID, owner, unblock condition), key decisions, last action and next action.
- **Blockers**: maintain stable `B-###` entries in the `## Blockers` section of `progress.md` with `open/resolved` status, affected phase, why blocked, attempted remedy and resolution. Include only current open blockers in the summary. Do not close a blocked phase without evidence.

The canonical PWF files are `task_plan.md`, `progress.md`, and `findings.md`. `summary.md` is derived; do not allow it to override them. A claim about testing is **not proof**: link actual command output or artifact and check the evidence against the current code. Redact secrets, customer data, credentials and sensitive log bodies.

## Host hooks and stop boundaries

- **OpenCode 2:** the native `opencode-planning-with-files` plugin (installed by this fork's `install.sh`) injects state on turns and participates in compaction. Installing the skill alone is not enough. On failure run the upstream diagnosis tools instead of bypassing a missing or invalid plan.
- **Cursor:** install the official [project-local hooks](https://github.com/OthmanAdi/planning-with-files/blob/master/docs/cursor.md) separately and *merge* `.cursor/hooks.json`, preserving existing hooks. `sessionStart` restores state for new chats; it is **not** a guarantee of injection at in-place compaction. Explicitly read the files on resume.
- Never enable automatic gated/autonomous stopping, commit, push, merge, deployment, deletion or other irreversible actions without the user's distinct authorization. Maintain the PStack approval rules.
- Keep the separate `show-me-your-work` TSV audit trail when its workflow requires it; reference evidence without duplicating the full trail.

## Handoff

Return the selected plan path, completed vs pending phases, exact last verified step, blockers and owners, decisions, evidence references, drift and the next safe action. If evidence is missing, report `unverified`, not `complete`.
